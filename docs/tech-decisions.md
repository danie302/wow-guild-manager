Each decision has a status:
- **Accepted**: decided.
- **Proposed**: recommended, waiting for confirmation.
- **Open**: still being discussed.

## Runtime environment: Docker

**Status:** Accepted

Every part of the system runs in a Docker container, so the whole stack starts locally with one command (`docker compose up`) and behaves the same on every machine.

Local containers:

| Container | Runs |
|---|---|
| `web` | Vite dev server, with hot reload from the mounted source |
| `api` | Express API server |
| `bot` | Discord bot |
| `worker` | Background jobs and scheduler |
| `postgres` | Database, with a named volume so data survives restarts |
| `redis` | Sessions, cache, and job queues |

- `api`, `bot`, and `worker` use the same image with different start commands.
- Database migrations run automatically when the `api` container starts (not when it restarts after a file change).
- Credentials (Discord app, Battle.net client) go in a `.env` file. A `.env.example` lists every variable.
- Images: `node:24-trixie-slim` for the app containers, `postgres:18-alpine`, and `redis:8-alpine` (with append-only file persistence).
- A one-shot `deps` service installs dependencies into the `node_modules` volumes on every `docker compose up`, and the other Node.js containers start after it finishes. This keeps dependencies current without rebuilding images and avoids parallel installs into the same volumes.
- In development, the server processes run with `tsx watch` and restart when any file in `apps/server/src` or `packages/shared/src` changes. Node's built-in TypeScript support was considered, but it can't resolve the `.js` import extensions that `NodeNext` uses for `.ts` files.

## Language: TypeScript

**Status:** Accepted

The web client, server, and shared packages are all TypeScript. Shared types and schemas mean the client and server can't drift apart without a compile error.

## Web client: React with Vite

**Status:** Accepted. Next.js was considered and rejected.

A single-page app built with Vite, React, React Router, and TanStack Query.

- React Router is used in library mode (`createBrowserRouter`), with the routes in `src/app/routes.tsx`. A guild's pages live under `/guilds/:guildId/...`, so each tab can show a different guild and links open the right one. The last guild opened is remembered in the browser.
- In development, Vite forwards `/api` to the API (`API_PROXY_TARGET`), so the browser only talks to one origin and the API needs no CORS setup.

**Why not Next.js:** Next.js comes with its own server, API routes, and server-side rendering. With Express as the backend, that would mean two servers with overlapping jobs, and a login cookie shared between them. Next.js is strongest for public sites that need SEO or server rendering. This app is an internal tool behind a login, so it wouldn't use those strengths.

## Backend: Express 5

**Status:** Accepted

Express serves the web client's API and handles the Discord OAuth2 login. Sessions use `express-session` stored in Redis.

- `createApp()` (`apps/server/src/api/app.ts`) builds the app from its dependencies without listening, so tests use it with Supertest. The `api` entry point creates the connections, builds the app, and listens.
- Configuration comes from environment variables, validated with Zod in `apps/server/src/config.ts` when a process starts. A missing or invalid variable stops the process with a message naming it.
- Errors are JSON with a code and no text: `{ "error": { "code": "NOT_FOUND" } }`. The codes and response types live in `packages/shared`. Unhandled errors return `INTERNAL_ERROR` with no details, and the stack trace is logged.
- `GET /api/health` checks PostgreSQL and Redis and returns 503 naming whichever is down.

### Login and sessions

- **Discord OAuth2** (authorization code flow) with only the `identify` scope. The code is exchanged on the server, the profile is read, and the access token is dropped. Guild data comes from the bot, so user tokens are never stored or sent to the browser. The OAuth2 calls sit behind a `DiscordOAuth` interface (`src/auth/discord-oauth.ts`) so tests use a fake Discord.
- **`state`** is 32 random bytes kept in the session, compared in constant time, and deleted after one use. The session is regenerated on login.
- **Sessions:** `express-session` with `connect-redis` on the node-redis client (keys `session:<id>`). Cookie `wgm.sid`: `httpOnly`, `SameSite=Lax`, `Secure` in production (with `trust proxy` for an HTTPS reverse proxy), 30 days, renewed on every request. Sessions store only the user ID.
- **Users** are created on first login (`users` table: Discord ID as text, name, avatar hash, language, time zone, theme). A new user's language and time zone come from the browser they log in from. `GET /api/me` returns the user or 401 `UNAUTHENTICATED`; `PATCH /api/me` changes their own settings; `requireUser` guards routes.
- **Configuration:** `SESSION_SECRET` is required. `WEB_ORIGIN` (where the browser opens the web app) builds the OAuth2 redirect URI. Without `DISCORD_CLIENT_ID`/`DISCORD_CLIENT_SECRET` the API still runs and the login page says login isn't set up. Empty variables count as not set.

## Repository layout: monorepo with pnpm workspaces

**Status:** Accepted

One git repository holds the web client, the server, and the code they share, each as its own workspace package.

```
wowGuildManager/
├─ apps/
│  ├─ web/                    React + Vite
│  │  ├─ src/
│  │  │  ├─ app/              App root, routes, layout, and the login guard
│  │  │  ├─ pages/            Roster, events, attendance, gear checks, dashboard, settings
│  │  │  ├─ components/ui/    Our UI kit (the only place that imports MUI)
│  │  │  ├─ api/              Calls to the server (TanStack Query)
│  │  │  ├─ i18n/             i18next setup and date formatting
│  │  │  ├─ locales/          English and Spanish translations
│  │  │  └─ test/             Test setup and helpers
│  │  └─ Dockerfile
│  └─ server/                 Express + discord.js + BullMQ
│     ├─ src/
│     │  ├─ domain/           Rules: sign-ups, waitlist, Tentative deadline, permissions, attendance (from story 012)
│     │  ├─ db/               Sequelize models and migrations
│     │  ├─ api/              Express routes, sessions, and errors
│     │  ├─ auth/             Discord OAuth2 and app users
│     │  ├─ bot/              Discord commands and buttons
│     │  ├─ jobs/             BullMQ queue, worker, and job handlers
│     │  ├─ integrations/     Discord (from story 012) and character lookup (story 017; Battle.net in 037) clients
│     │  ├─ i18n/, locales/   Server translations (bot replies, DMs, Discord posts)
│     │  └─ entrypoints/      api.ts, bot.ts, worker.ts
│     ├─ test/                Test setup (test database and Redis)
│     └─ Dockerfile
├─ packages/
│  └─ shared/                 Zod schemas, API types, and game data
├─ docs/
├─ docker-compose.yml
├─ pnpm-workspace.yaml
└─ tsconfig.base.json
```

### What goes where
- **`apps/web`** talks to the server only over HTTP. It never touches the database or Discord directly.
- **`apps/server`** holds the whole backend. Its three entry points run as the `api`, `bot`, and `worker` containers.
- **`packages/shared`** holds only code that must also run in the browser: Zod schemas, API response types, and the game tables (races by faction, classes by race, combat roles by class). It must not import anything server-only, such as Sequelize.
- **Domain rules live in `apps/server/src/domain`,** not in `packages/`, because they use the database (transactions, row locks, models), which only exists on the server.

### Dependency rules
```
web ──→ shared ←── server
```
- `shared` depends on nothing except Zod.
- `web` and `server` never import each other.
- Inside the server, `domain/` doesn't import Express or discord.js, so it can be tested without a running server or bot, and all three entry points use it the same way.

### Why pnpm
- **Strict dependencies:** a package can only import what its own `package.json` declares, so `web` can't import a server library by accident.
- **`pnpm deploy`** builds a minimal folder with one package and only its dependencies, used for the production server image.
- **Per-package commands:** `pnpm --filter server test`, `pnpm --filter web build`.

### Package names and the shared package
- The packages are `@wgm/web`, `@wgm/server`, and `@wgm/shared`.
- `@wgm/shared` has no build step: its `exports` point at its TypeScript source, which Vite and the server's TypeScript tooling read directly. How the production server image handles it is decided when deployment is planned.

npm workspaces were considered: they need no extra tool but aren't strict about dependencies. Turborepo and Nx aren't needed at this size and can be added later.

### Docker and the monorepo
- The Docker build context is the repository root, because every image needs `packages/shared`. A `.dockerignore` keeps the context small.
- Production images use multi-stage builds. The server image contains only the compiled server and its dependencies, not the web client.
- In development, the repository is mounted into the containers for hot reload, and `node_modules` lives in Docker volumes so Linux-built dependencies don't clash with the host's.
- The `api`, `bot`, and `worker` containers start `tsx` directly (`exec` in their `command`), not through `pnpm` scripts. When pnpm receives SIGTERM it kills its children with SIGKILL, which would skip each process's graceful shutdown.

## Backend processes: one codebase, three processes

**Status:** Accepted

The API server, Discord bot, and worker live in the same codebase and run as three separate processes. They all use the same domain rules (combat roles by class, slots, waitlist, the Tentative deadline, permissions), so the rules are written once. A process can be split into its own service later if it needs to scale on its own.

Each process validates only the environment variables it needs. `src/config.ts` has a base Zod schema (database, Redis, logging) that each process extends: the API adds `PORT`, the session secret, and the login settings, and the bot adds `DISCORD_BOT_TOKEN`. So the API runs without a bot token, and the bot exits with a clear message when it's missing. The worker uses the base schema.

## Database: PostgreSQL

**Status:** Accepted

The data is relational (guilds, members, characters, events, sign-ups, attendance), and sign-ups need strong guarantees under concurrency.

**Slot locking happens in PostgreSQL, not in Redis.** When a Discord button click fills a slot, the sign-up runs in a transaction that locks the event row (`SELECT … FOR UPDATE`). Two clicks for the last slot are handled one after the other, and if anything fails, the whole change is rolled back together.

## ORM: Sequelize 6

**Status:** Accepted

Sequelize was chosen over Drizzle ORM for its stability and its large community. Version 6 is the stable release.

### How we use it
- **Typed models.** Models extend `Model<InferAttributes<…>, InferCreationAttributes<…>>` and declare their fields with `declare`, so queries return typed objects.
- **Automatic transaction propagation.** Sequelize is configured with CLS (`Sequelize.useCLS`), so every query inside `sequelize.transaction(async () => { … })` joins that transaction automatically. Without it, a query that forgets `{ transaction: t }` runs outside the transaction with no error, and the slot lock stops protecting sign-ups. The CLS namespace is a small adapter over Node's built-in `AsyncLocalStorage` instead of `cls-hooked`, which Sequelize's docs suggest but which hasn't been maintained since 2017.
- **Row locks for sign-ups.** The sign-up transaction loads the event with `lock: Transaction.LOCK.UPDATE` before counting slots.
- **Migrations.** Migrations are written by hand with `sequelize-cli` and run automatically when the `api` container starts, before it listens (`bot` and `worker` never run them, so they can't race). Every model change needs a matching migration in the same change. Migration files are CommonJS JavaScript, because `sequelize-cli` can't load TypeScript or ES modules.
- **Naming.** Models use `underscored: true`: attributes are camelCase in code and snake_case in the database.
- **Where to look.** `apps/server/src/db/README.md` documents the typed model pattern, transactions, and the migration commands.
- **Validation stays in Zod.** Zod schemas in `packages/shared` are the source of truth for input validation. Sequelize model validations are only used for database-level guarantees (e.g. not null).
- **A test for concurrent sign-ups.** A test sends several sign-ups for the last slot at the same time and checks that only one gets it.

### Options considered

| | Drizzle ORM | Sequelize |
|---|---|---|
| Style | SQL-like query builder, plus a relational query API | Active Record models (classes with methods) |
| TypeScript | Built for it. Types are inferred from the schema | Added later. Models need extra type declarations, and results with `include` are loosely typed |
| Schema and migrations | The schema is TypeScript. `drizzle-kit` generates migrations from schema changes | Models and migrations are written separately and can drift apart |
| Row locks (`FOR UPDATE`) | Supported in the query builder | Supported with `lock` inside a transaction |
| Zod integration | `drizzle-zod` generates Zod schemas from tables | No official integration |
| Hooks and model validation | None. Validation is done with Zod | Built in |
| Maturity | Newer (2022). Faster-moving, with some breaking changes between versions | Mature (2011). Large community and many answered questions |
| Performance and weight | Light. Queries map closely to SQL | Heavier. Queries with many `include`s can be inefficient |
| Learning curve | Needs comfort with SQL | Easier without SQL knowledge |

Drizzle was the stronger fit for type safety and generated migrations. Sequelize was chosen for its maturity and community. The points under "How we use it" cover its main weaknesses for this project.

## Cache, sessions, and job queues: Redis with BullMQ

**Status:** Accepted

Redis stores:
- Web sessions.
- Cached Battle.net and Discord responses.
- BullMQ job queues.

BullMQ handles:
- **Delayed jobs:** the Tentative reminder and deadline, and the gear check 12 hours before a raid. Each is one job per event, scheduled for its exact time.

**How per-event jobs are kept correct.** The Tentative deadline and reminder time are configurable per guild and per event, so their jobs move often:
- Every job has a fixed ID built from its type and event (e.g. `tentative-deadline-<eventId>`; BullMQ doesn't allow `:` in job IDs). Rescheduling means removing the job with that ID and adding it again, so there are never duplicates.
- Jobs are rescheduled when an event's time or deadline changes, removed when the event is cancelled, and rescheduled for every upcoming event without its own deadline when the guild's settings change (skipping events whose new deadline would already have passed).
- Every job checks the current data when it runs: if the event was cancelled or its deadline moved, it does nothing. A job left behind by a missed reschedule can't replace anyone at the wrong time.

A periodic check (one job every minute looking for due events) was considered. It needs no rescheduling, but runs all the time even with no events. Per-event jobs were chosen.
- **Repeating jobs:** creating instances of recurring events.
- **Retries:** for failed Battle.net or Discord calls.

### How the job queue is set up

The code is in `apps/server/src/jobs/`:
- **One queue** (`jobs`) for every job; the job name picks the handler. Separate queues can be added later if one kind of job needs its own concurrency or rate limit.
- **Typed jobs:** `definitions.ts` maps each job name to its payload type, and `JobQueue` only accepts those names and payloads, so a wrong payload is a TypeScript error. The worker needs a handler for every name. Payloads are plain JSON with IDs, not whole records, because jobs re-read the current data when they run.
- **`JobQueue`** is the only way to add jobs, from any process: `enqueue` (run now), `schedule` (run at a time, under a fixed ID that replaces any existing job), `unschedule`, `repeat` (a BullMQ job scheduler with a fixed ID, on an interval or cron pattern in UTC), and `stopRepeating`.
- **Retries:** 5 attempts with exponential backoff starting at 30 seconds. A handler throws `UnrecoverableError` to fail without retrying. Every failed attempt is logged as a warning, and the final failure as an error.
- **Cleanup:** completed jobs are deleted right away, so their fixed IDs can be used again. Failed jobs are kept for 7 days.
- **A running job can't be replaced.** `schedule` and `unschedule` throw `JobRunningError` if the job with that ID is running at that moment.
- **Durability:** Redis runs with `--appendonly yes`, so pending jobs survive a restart of Redis. A job cut off when the worker is killed goes back to the queue. On SIGTERM the worker waits for running jobs to finish.

### Redis clients: node-redis, and ioredis inside BullMQ

Our code uses the official `redis` package (node-redis): the health check and sessions. `connect-redis`, the `express-session` store, only supports node-redis.

BullMQ uses ioredis (5.x), its default client. BullMQ 6 also has a node-redis adapter, which would mean one client for everything, but it was new (released mid-2026) while ioredis is what BullMQ's documentation and test suite use, and the time-based jobs depend on it. Only `src/jobs/` touches BullMQ, and it passes BullMQ a connection URL, so our code never imports ioredis directly. Switching to the adapter later only changes `redisConnection()` in `src/jobs/queue.ts`.

Clients are created with `disableOfflineQueue: true`, so commands fail right away while Redis is down instead of waiting for it to come back.

## Discord bot: discord.js over the Gateway

**Status:** Accepted

The bot uses discord.js and connects to the Discord Gateway, which is an outgoing WebSocket connection. This means it works on a local machine without exposing a port or using a tunnel. Discord also accepts `http://localhost` as an OAuth2 redirect URL, so the login works locally too.

How the bot is set up:
- **Intents:** `Guilds` and `GuildMembers`. `GuildMembers` is privileged, so it has to be turned on in the Developer Portal. It's needed to see members leave the server and to keep the Officer role in sync. The bot doesn't read message content.
- **Slash commands are registered per Discord server,** not globally, because per-server commands appear immediately. The bot registers them for every server when it connects and when it joins a new one. Each command is a `SlashCommand` (definition plus `execute`) in `apps/server/src/bot/commands/`, listed in `commands/index.ts`.
- **Replies only the user should see** use `MessageFlags.Ephemeral`. If a command throws, the bot logs the error and replies with a generic ephemeral message.

### Discord data in the API

**Status:** Accepted

The login only has the `identify` scope, so the API can't ask Discord about a user's servers with the user's token. When it needs Discord data (the servers the bot is in, a user's permissions and roles in a server, a server's roles), it calls Discord's REST API with the bot token. These calls only happen at specific moments (guild setup, changing the Discord connection, searching the server's members in the add-member form), never on every request, so Discord API usage doesn't grow with the number of users.

- The calls sit behind a `DiscordDirectory` interface in `src/integrations/discord/`, so tests use a fake.
- Responses are cached in Redis for a short time, to stay within Discord's rate limits.
- The API reads `DISCORD_BOT_TOKEN` as optional: without it (or `DISCORD_CLIENT_ID`, which the bot invite link needs) the API runs, but the Discord routes answer 503 `DISCORD_NOT_CONFIGURED`.
- Servers and members are cached for 60 seconds. The bot's server list isn't cached, so a server shows up right after the bot is added. If Discord fails, guild pages still load without the server and role names.
- The bot clears the cached member or server when roles or members change (`src/bot/cache-events.ts`), so a change in Discord shows up on the next request. The cache only waits out its 60 seconds when the bot is down.
- Rules that use this data (who can connect which server) live in `src/domain/guilds.ts`. Domain rules throw `DomainError` with an API error code, and `api/errors.ts` maps each code to its HTTP status.
- Permissions in a server are worked out from the member's roles (and the server owner has every permission), as Discord does. Manage Server or Administrator counts as managing the server.

Two options were rejected for the setup data: the bot copying servers, roles, and members into PostgreSQL from Gateway events (more code, and the copy can fall behind), and the API asking the bot over Redis (a protocol of our own, and the API would depend on the bot running). Officer access is the exception, below: it's needed on every request, so it is copied.

### Officer access

**Status:** Accepted

A user is an Officer of a guild while they have its Officer role in its Discord server. Who has it is stored in `guild_officers` (guild, Discord user ID), the source of truth for Officer access. The API reads only this table, so checking access costs no Discord API calls.

- **The bot keeps it current from Gateway events** (`src/bot/server-sync.ts`): a member's roles change, they join or leave, the Officer role is deleted, or the bot leaves the server. Gateway events are pushed over the bot's open connection and don't count against Discord's REST rate limits.
- **Full resync at specific moments:** each time the bot connects (or reconnects with a new session, when events may have been missed) it reads every server's members over the Gateway and replaces each guild's Officers. When a guild is created or its Officer role changes, the API reads the role's members once with REST.
- **The trade-off:** while the bot is down, a removed Officer role keeps working until the bot reconnects and resyncs.
- `src/domain/access.ts` works out a user's access (Guild Master from the guild, Officer from the table), `src/domain/permissions.ts` maps each action to the ranks allowed, and `requireGuildPermission(action)` guards each guild route.
- Checking Discord on every request (with a short cache) was tried first and replaced: its Discord API usage grows with the number of users.

## Character lookup: an interface until Battle.net supports Forever

**Status:** Accepted (story 017)

The gear checks (and, later, registering characters from Discord) read characters from the game. Blizzard hasn't published a Battle.net API for World of Warcraft: Forever, so the app reads them through a `CharacterLookup` interface in `src/integrations/character-lookup/`, and the real Battle.net client is story 037.

- A lookup returns a typed result: `found` (with the data and when it was fetched), `not_found`, or `unavailable` (`not_configured` or `error`). Callers handle each one; lookups don't throw for these cases.
- Until story 037, `createCharacterLookup()` returns the "unavailable" implementation, so callers fall back to data entered by hand. No Battle.net environment variables exist yet; story 037 adds them and returns the real client when they're set.
- A character is looked up by name only, because Forever has no realms. Story 037 adds whatever else Blizzard's API needs.
- Lookups run in the worker (the job handlers receive the lookup), never in page requests or bot interactions. Nothing calls it yet: story 018 dropped the lookup from `/register`.
- Tests use `FakeCharacterLookup` (`apps/server/test/fake-character-lookup.ts`).
- Equipment slots are a game table in `packages/shared` (`EQUIPMENT_SLOTS`), since the web app needs them for the gear check and the guild's enchant settings.

### Requests to join and direct messages

**Status:** Accepted (story 018)

- `/register` is a request to join the roster, without a character, stored in `registrations` (one pending request per person and guild). Officers add characters in the web app. Registering characters from Discord, checked against Battle.net, will be reviewed once Blizzard's API supports Forever.
- Approving or rejecting in the web app enqueues a `registration-reviewed` job, and the worker sends the direct message. Discord REST calls stay off the request path.
- Direct messages go through a `DirectMessenger` interface (`src/integrations/discord/direct-messages.ts`) that only the worker uses, with the bot token. A user who doesn't accept direct messages isn't an error (the job isn't retried); other failures are retried by BullMQ. Without `DISCORD_BOT_TOKEN` the worker skips them.
- A direct message is written in the language the person used `/register` in.
- Approving adds the member, or restores a removed one with their characters, through `addMember` inside the approval's transaction. Domain functions use `transaction()` from `src/db/transaction.ts`, which joins the current transaction when there is one, so they can be combined.
- `/main` changes the member's main right away. Its option suggests their characters with Discord autocomplete: a command can have an `autocomplete` handler, which reads the database only (no Discord REST).
- Buttons on a command's replies (from story 038, e.g. `/character remove`'s Confirm and Cancel) are handled by the command's `button` handler. Their custom IDs start with the command name and `:` and carry what the click needs (e.g. `character:remove:<character ID>`), and the handler checks everything again on click: who clicked, and whether the data still allows it.

### Event posts

**Status:** Accepted (story 022)

- The worker publishes, edits, and deletes event posts with Discord's REST API and the bot token, not the bot process. The API and the bot don't need a channel between them, Discord REST calls stay off the request path, and BullMQ retries when Discord fails.
- An `event-post` job (payload: the event ID) is enqueued after every change: an event is created, edited, or cancelled, a series is created or edited (for each of its future events), or the guild's events channel or Discord language changes (for every upcoming event that isn't cancelled). The handler reads the event again and brings the post up to date, so it doesn't matter how many changes one run covers.
- Jobs aren't deduplicated by a fixed ID, because BullMQ ignores a job whose ID is already running, and that change would be lost. Instead, runs for the same event take turns on a PostgreSQL advisory lock (`pg_advisory_xact_lock`), so two runs never post the same event twice. It's an advisory lock rather than the event row's lock, so sign-ups (which lock the row) never wait for Discord.
- The event stores the post's channel and message IDs. If the message no longer exists, the handler posts it again. If the events channel changed, it posts in the new one and deletes the old message. A cancelled event's post stays where it is, marked as cancelled, and a cancelled event that was never posted isn't posted.
- Stopping a series deletes the posts of the future events it removes, with an `event-post-delete` job that carries the channel and message IDs (the event no longer exists).
- If Discord refuses for a reason retrying won't fix (missing permissions, the channel is gone), the handler stores the reason on the event (shown in the Discord post tab) and doesn't retry. Other failures are retried by BullMQ. Failed posts are retried only when something may have fixed them, never on a timer: a refusal nobody fixes would be retried forever, and Discord blocks a bot that gets too many refused requests (10,000 in 10 minutes), which would take it down for every guild. The bot retries them as soon as the permissions may be back: on the Gateway events for a channel or role change in the server, or a new role for the bot, it enqueues `event-post` for that guild's upcoming events with an error, and on each connect for every server it's in, in case it missed events while down (`src/bot/post-retries.ts`, no Discord API calls). Editing the event, or changing the guild's events channel or language, retries it too.
- The worker's hourly job (the same run that extends recurring series) enqueues the upcoming events that were never posted: the new events of series, and any whose job was lost. Two partial indexes (events without a post, and events with a failed post) keep both searches to the few events in that state, however many events there are, and the jobs are added in bulk.
- The post is a Discord embed built by `eventPostEmbed` (`src/domain/event-post.ts`) in the guild's language, with Discord timestamps so each reader sees their own time. The API's preview endpoint returns the same embed, and the web app renders it, so the preview matches the real post.
- The post is laid out like the raid bots players know (Raid-Helper): a header with who created the event, how many signed up, and when (Discord timestamps), a column per role (inline fields) with each character's class icon, sign-up number across the event, and name, then the waitlist and who declined.
- The class and role icons are the bot application's own emojis (Discord allows 2000 per app, usable only by its bot), named `wgm_<class>` and `wgm_<role>` and uploaded from `apps/server/assets/emojis/` by `pnpm discord:emojis`. The images aren't in the repository, since the official icons are Blizzard's. The worker and the API read the list with the bot token (`GET /applications/@me`, then its emojis) at most once an hour per process (`postEmojiSource`), and fall back to no class icons and 🛡️ ➕ ⚔️ when they're missing or Discord fails.
- The API needs the bot's user ID to check its permissions; it's the application's `DISCORD_CLIENT_ID`.
- Sign-ups (story 023) coalesce the post's edits: each one schedules `event-post` for the end of the current few-second window, with a job ID per event and window (`event-post-<eventId>-<window>`). Every sign-up in that window lands on the same job, which reads the final state when it runs, so a burst of sign-ups makes one edit per window instead of one each (Discord limits edits per channel). The window is in the ID, rather than one fixed ID per event, because BullMQ ignores a job whose ID is already running: a sign-up that arrives while the edit runs is in the next window, so it gets its own job and isn't lost. Other changes (editing the event, the guild's settings) still enqueue it right away.
- The events channel picker lists the server's text channels through `DiscordDirectory` (cached like the roles), showing only the ones where the bot can see, write, and post embeds.

### Sign-ups from Discord

**Status:** Accepted (story 023)

- The post has **Sign up** and **Declined** buttons. Sign up opens a form only the member sees, with a character select, a role select, and Confirmed and Tentative buttons. Every step re-reads the data, since the form can be answered much later, and the custom IDs carry what each step needs (e.g. `signup:confirmed:<event>:<character>:<role>`).
- Buttons and selects that aren't a command's replies go through a `ComponentHandler` (`src/bot/commands/types.ts`), picked by the first part of the custom ID. The sign-up one is `src/bot/sign-up.ts`.
- The rules live in `src/domain/sign-ups.ts`: who can join each event type, the class and role check, and slot or waitlist. `signUp` and `decline` run in one transaction that locks the event row first, so parallel sign-ups can't both take the last slot.
- `sign_ups` has one row per member and event (a unique index), with the character, role, status, placement (slot or waitlist, null when Declined), and `signed_up_at`, the waitlist's order. Rows stay when a member or character is removed, so attendance keeps its history.
- After a sign-up or decline, the bot schedules the post's update through `scheduleEventPostUpdate`, which gathers a few seconds of sign-ups into one edit (see "Event posts").
- Every change that can open or remove a slot (a decline, a role change, editing the slots, removing a member or character) calls `balanceSlots` with the event locked: extra participants move to the front of the waitlist (most recent first, by `signUpsLosingSlots` in `packages/shared`, which the event form also uses to warn before saving) and open slots go to the earliest waitlisted characters. Removals lock each affected event in turn, in ID order.
- These changes return a `SignUpChanges` (promoted, moved to the waitlist, rescheduled participants, events whose posts changed) instead of messaging: the route or bot command hands it to `notifySignUpChanges`, which enqueues the direct messages (`waitlist-promoted`, `moved-to-waitlist`, and one `events-rescheduled` per member, however many of their events moved) and the post updates. Each message job re-reads the data and says nothing if it no longer holds.

## IDs: UUID v7

**Status:** Accepted

Every table's primary key is a UUID v7, generated by PostgreSQL 18 (`uuidv7()`), and foreign keys are UUIDs too. Table-to-table links with no data of their own (like `guild_officers`) use a composite key instead.

- IDs appear in URLs and API responses. Sequential numbers would let anyone count guilds or probe which IDs exist; UUIDs can't be guessed. Access is still checked on every request.
- Version 7 starts with a timestamp, so new rows land at the end of the index like sequential IDs, instead of scattering across it like random v4 UUIDs.
- A separate public UUID next to an internal integer key was considered: lighter joins, but two IDs per table and the risk of exposing the internal one.
- `uuidSchema` in `packages/shared` validates IDs from URLs; a malformed ID is a 404.

## Validation: Zod

**Status:** Accepted

Zod schemas in `packages/shared` validate API requests on the server and forms on the web client, from a single definition.

- Game data (factions, races, classes, combat roles, professions) lives in `packages/shared/src/game.ts` as stable snake_case codes (`night_elf`, `first_aid`), with their English display names next to them. The database and the API use the codes.
- Custom checks (e.g. a class that a race can't be) set the Zod issue message to an error code such as `CLASS_NOT_FOR_RACE`, never to text.

### Offensive word filter

**Status:** Accepted

Names people choose (for now, the guild name) are checked against lists of offensive words, so the web form warns while typing and the server rejects them with the code `NAME_NOT_ALLOWED`.

- It uses [`@2toad/profanity`](https://www.npmjs.com/package/@2toad/profanity) (MIT, no dependencies), which has word lists for 12 languages. We check English and Spanish; adding a language means adding its code to the list in `packages/shared`.
- Only `packages/shared` imports the package, behind one function (`hasOffensiveWords`), so it can be replaced without touching callers.
- Matching is on whole words with Unicode-aware boundaries (`wholeWord`, `unicodeWordBoundaries`), so words that only contain an offensive word (e.g. "vehículo") aren't blocked. Matching ignores case.
- The package doesn't ignore accents (its list has "cabrón" but not "cabron"), so the wrapper also checks the name without accents against the lists without accents.
- Limits: it only knows the forms in its lists (some plurals are missing) and doesn't catch tricks like `l33t` spellings or separators. Words can be added with `addWords` if needed.
- It ships every language's list (about 94 kB before compression) in the web bundle, since the package can't load one language at a time.
- A moderation service was rejected: it adds an external dependency, latency, and cost for a name only the guild's own members see. Writing our own lists (e.g. from LDNOOBW) was also considered.

## Testing: Vitest and Supertest

**Status:** Accepted

Vitest runs unit tests in both the web client and the server. Supertest runs HTTP tests against the Express app.

- Each package has its own Vitest config, and the root `pnpm test` runs them all. Test files (`*.test.ts`, `*.test.tsx`) go in a `__tests__` folder inside the folder of the code they test, so folders list only code while tests stay one step away. Server tests that aren't about one file go in `apps/server/test/`. A component that grows into several files gets its own folder (`AppShell/AppShell.tsx` plus an `index.ts` that re-exports it, and its own `__tests__/`), instead of a folder per file from the start.
- Web tests run in jsdom.
- **Test database:** server tests use a separate database in the same PostgreSQL container (`<POSTGRES_DB>_test`, from `TEST_DATABASE_URL`). A global setup drops and recreates it at the start of every run, and refuses to touch any database whose name doesn't end in `_test`. During tests, `DATABASE_URL` points at it.
- **Test Redis:** server tests use Redis database 1 (`TEST_REDIS_URL`), which the global setup empties on every run and refuses to do for database 0, the one the app uses. During tests, `REDIS_URL` points at it. Job tests also give every test its own queue name.
- Server test files run one at a time (`fileParallelism: false`), because they share the test database and empty its tables. Tests inside a file still run in order.
- Tests run inside the Docker containers (`docker compose exec api pnpm test`), where the database is reachable and the environment variables are set.

## Internationalization: i18next

**Status:** Accepted

The app supports English and Spanish (see the Languages section of `requirements.md`). i18next is used everywhere: `react-i18next` in the web client, and i18next directly in the API, bot, and worker. One library means the same translation file format, plural rules, and interpolation on both sides.

- **Translation files:** JSON files per language (`locales/en`, `locales/es`) in each app.
- **Game terms aren't translated.** Class, race, and profession names, combat roles, and ranks are shown in English in both languages. Their display names come from `packages/shared`, so the web client and the bot always show them the same way.
- **Typed keys:** translation keys are typed, so a missing or misspelled key is a TypeScript error.
- **Same keys in both languages:** a test fails if English and Spanish don't have exactly the same keys.
- **The API returns error codes, not text.** Validation and domain errors come back as codes (e.g. `SLOT_FULL`, `CLASS_CANNOT_FILL_ROLE`) with their parameters, and the client translates them. Zod errors are mapped to codes the same way.
- **Dates and numbers** are formatted with the built-in `Intl` APIs for the user's language and time zone. In the web client, `useFormat()` is the only formatter: it reads the user's IANA time zone from `/api/me`. Time zones are validated with `Intl.DateTimeFormat` on both sides, so no time zone database is bundled.
- **Discord:** the bot picks the language per message as described in `requirements.md`, using the interaction's locale for replies one member sees. Slash commands are registered with Discord's name and description localizations.

How it's set up:
- **One namespace per app** (`translation`), in `apps/web/src/locales/<lang>/translation.json` and `apps/server/src/locales/<lang>/translation.json`. Keys are grouped by screen or feature (`status.title`, `commands.ping.reply`). Plurals use i18next's `_one`/`_other` suffixes with a `count` parameter.
- **Typed keys** come from the English file, declared in `i18n/i18next.d.ts` in each app. `TranslationKey` is the type to use for props or parameters that take a key.
- **Web client:** a dedicated i18next instance with `react-i18next`. The language comes from the saved choice, then the browser's languages, then English; switching it re-renders without a reload and updates `<html lang>`. `useFormat()` formats dates and numbers with `Intl`.
- **Server:** one i18next instance; code gets a function fixed to one locale with `translator(locale)`. The bot passes `{ locale, t }` to every command.
- **API error shape:** `{ error: { code } }`, plus `issues` for `VALIDATION_ERROR` (one `{ field, code, params? }` per invalid field). `toValidationIssues` in `packages/shared` maps Zod issues to these codes, keeping the shared schemas' rule codes.
- **Language names** in the picker are shown in their own language ("English", "Español"), so they aren't translation keys.

## UI components: Material UI behind compound components

**Status:** Accepted

The web client uses Material UI (MUI), themed with the tokens from `docs/design/` (Archivo, square corners, the color tokens for both themes).

App code never imports MUI directly. It uses our own components in `apps/web/src/components/ui`, built with the **compound components** pattern: a parent component that shares state with named child parts, so pages describe the structure without knowing how it's implemented. For example:

```tsx
<RoleSection role="healer">
  <RoleSection.Header />
  <RoleSection.Slots />
  <RoleSection.Waitlist />
</RoleSection>
```

- Only `components/ui` imports `@mui/*`. An ESLint rule (`no-restricted-imports`) blocks MUI imports anywhere else.
- Component props use our own types, not MUI's, so changing the design library later only changes `components/ui`.
- The MUI theme lives next to those components and is built from the design tokens.
- The tokens (`src/components/ui/tokens.ts`) are copied from the prototype for both themes. They're also set as CSS variables under `[data-theme="dark"]` and `[data-theme="light"]`, so our components use the same names as the design (`var(--sf2)`). MUI's `nativeColor` option lets its palette use the `oklch()` colors.
- Archivo is self-hosted with `@fontsource-variable/archivo`, so the app doesn't load fonts from Google.
- Icons are the prototype's SVG paths in an `Icon` component, not an icon package.
- `src/components/ui/index.ts` is the only entry point pages use.
- **Theme switching:** `useThemeMode()` wraps MUI's `useColorScheme`, which sets `data-theme` on `<html>` and remembers the choice in the browser. The user's saved theme is applied after login.
- **Use MUI as much as possible inside the kit** (decided on 2026-10-21). Every control is built on its MUI counterpart, styled with our tokens, so keyboard use, focus, and accessibility come from MUI: `Button` (MUI `Button`), `TextField` and `Stepper` (`InputBase`, `IconButton`), `Select` (MUI `Select` with a themed menu, also in the sidebar's guild switcher), `Checkbox` and `CheckboxGroup` (`Checkbox`, `FormControlLabel`, `FormGroup`), `RadioList` (`RadioGroup`, `Radio`), `ChoiceGroup` and `FilterChips` (`ToggleButtonGroup`, so their options are buttons with `aria-pressed`), `Tabs`, `Tag` (`Chip`), `Notice` (`Alert`), `Icon` (`SvgIcon`), and the dialogs. Plain `Box` is only for layout (lists, headers, columns, cards) and for things MUI core doesn't have (the month calendar, the stacked slot bar). Ripples and shadows are turned off to match the flat design.
- **Searchable lists** use `ComboBox` (MUI `Autocomplete` inside). It adds about 160 kB to the bundle (see story 035's technical debt); if that becomes a problem, it can move to MUI's headless `useAutocomplete` without changing its props.

## Toolchain versions

**Status:** Accepted

- **Node.js 24 LTS,** pinned in `.nvmrc` and in `engines` (`>=24 <25`). The Docker images use the same major version.
- **pnpm through corepack:** the `packageManager` field in the root `package.json` pins the exact pnpm version, and corepack (bundled with Node.js 24) installs it, so everyone uses the same one.

## File storage: storage interface

**Status:** Accepted

Uploaded files (guild images) go through a small storage interface (save, read, delete) in `apps/server/src/storage/file-storage.ts`. In development, it writes to the `uploads` Docker volume (`UPLOADS_DIR`, `/uploads`). In production, it can be switched to an S3-compatible object store without changing the rest of the code. The production provider is chosen when deployment is planned. Tests use the in-memory implementation.

- **Images are processed with sharp:** cropped square, resized to 256×256, and re-encoded as WebP. Re-encoding drops metadata (EXIF, location) and anything hidden in the file. Only PNG, JPEG, and WebP up to 5 MB are accepted; the type is checked from the file's contents, not only its declared type.
- **Uploads go with the rest of the form:** the guild settings page saves in one multipart/form-data request (multer reads it into memory, within the size limit), so the image and the other settings apply together or not at all.
- **Images are served by the API** to people who can open the guild, not from a public folder. Each upload gets a new storage key, which is part of the image URL, so browsers can cache it for good and never show a stale one.
